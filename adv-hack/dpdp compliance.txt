For your **CPGRAMS-style grievance webapp**, I would not create dozens of separate DPDP pages. A practical DPDP-oriented UX can be covered with a focused set of pages and flows.

> **Important:** These are pages/features to support DPDP-oriented privacy compliance, not a guarantee of legal compliance. Final legal requirements should be validated against the applicable DPDP Act/Rules and your organisation's role.

## Recommended DPDP page structure

### 1. Public Privacy Pages

| Page                            | Route                | Purpose                                                                                                       | Priority         |
| ------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------- |
| **Privacy Notice**              | `/privacy`           | Explain what personal data is collected, why, how it is used, retention, sharing, rights, grievance mechanism | 🔴 Essential     |
| **Cookie / Tracking Notice**    | `/privacy/cookies`   | Explain non-essential cookies/tracking if your site uses them                                                 | 🟡 If applicable |
| **Data Retention Policy**       | `/privacy/retention` | Explain categories of data and retention/deletion approach                                                    | 🟡 Recommended   |
| **Security & Data Protection**  | `/privacy/security`  | Explain security safeguards at a high level                                                                   | 🟡 Recommended   |
| **Grievance / Privacy Contact** | `/privacy/contact`   | Privacy-related contact/grievance mechanism                                                                   | 🔴 Essential     |

You don't necessarily need all of these as independent pages. They can be sections under `/privacy`.

# 2. Login / Signup Privacy Screens

These are particularly important because the user is providing personal information.

### `/login`

```text
Login

Mobile Number
[________________]

[Send OTP]

Privacy Notice
Your information will be processed to authenticate
your account and provide access to your complaints.

[View Privacy Notice]
```

### `/login/otp`

```text
Verify Mobile Number

OTP sent to +91 XXXXX XXXXX

[ _ _ _ _ _ _ ]

Resend OTP
Change mobile number
```

No privacy consent should be bundled into the OTP itself.

---

### `/signup`

```text
Create Account

Name
Mobile
Email (optional)

Preferred Language

[Continue]
```

Then:

### `/signup/privacy`

This should be a dedicated privacy/consent step.

```text
Before you continue

Privacy Notice

We collect your information to:
• Create and secure your account
• Register and process complaints
• Communicate regarding your complaint

[Read full Privacy Notice]

Required
☐ I acknowledge and agree to the processing
  necessary for the requested service.

Optional
☐ I want to receive optional notifications.

[Continue]
```

**Do not pre-check optional consent.**

# 4. My Data / Data Access

### `/privacy/data`

or:

```text
/account/privacy/data
```

Show the user what categories of personal data the system holds.

Example:

```text
My Data

ACCOUNT
Name
Mobile number
Email
Preferred language

COMPLAINTS
Complaint information
Case IDs
Submitted documents

PREFERENCES
Language
Notification preferences

CONSENT
Consent records
Privacy notice version
Consent timestamps

[Request a copy of my data]
```

The important architectural point is that this must be **user-scoped**.

User A must never see User B's information.

# 5. Consent Management

### `/privacy/consent`

Show consent history and current status.

```text
Consent & Preferences

Required service processing
ACTIVE
Required for providing the requested service

Optional notifications
ACTIVE
[Withdraw]

Consent history

Privacy Notice v1.2
27 Aug 2026
Language: Gujarati
Status: Accepted
```

The system should maintain consent metadata rather than simply:

```text
consent = true
```

For example:

```text
purpose
noticeVersion
language
status
consentedAt
withdrawnAt
method
```

# 6. Consent Withdrawal

This can be a separate page or modal.

### `/privacy/consent/withdraw`

Example:

```text
Withdraw Optional Consent

Optional notifications

Currently:
ACTIVE

If you withdraw:
You will no longer receive optional notifications.

[Cancel]

```

Don't provide a misleading "withdraw all consent" button if some processing is necessary to provide the service.

# 12. Security / Account Management

### `/account/security`

This isn't strictly a "DPDP page", but it is important for protecting personal data.

Include:

```text
Account Security

Mobile number
Verified ✓

Recent login
27 Aug 2026

Active sessions

[Sign out of other sessions]
```

For an OTP-based system, this is preferable to inventing a password-management system.

# 13. Child / Minor Flow

If the service is available to children or could reasonably process children's data, you should have a dedicated flow rather than treating it exactly like an adult account.

Possible route:

```text
/parent-consent
```

Flow:

```text
Child account request
        ↓
Parent / guardian verification
        ↓
Consent
        ↓
Account activation
```

Whether and exactly how this is required depends on the applicable DPDP requirements and your user population, so this should be confirmed legally before implementation.

## The most important UX decision

Don't make the website look like a legal compliance portal.

The user should experience it as:

```text
LOGIN
   ↓
PRIVACY NOTICE
   ↓
CONSENT
   ↓
OTP
   ↓
ACCOUNT
   ↓
COMPLAINT
   ↓
MY CASES
   ↓
PRIVACY & DATA
      ├── My Data
      ├── Consent
      ├── Correct
      ├── Delete
      ├── Requests
      └── Grievance
```

That is much cleaner than adding 10–15 privacy links throughout the application.

And for **your existing build specifically**, I would keep the current complaint/dashboard pages visually unchanged and introduce **Privacy & Data as a new authenticated section**, rather than redesigning the whole application around DPDP.
